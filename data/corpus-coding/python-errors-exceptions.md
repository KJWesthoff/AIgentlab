# Python exceptions and error handling

Python error handling uses try/except blocks: code in `try` runs until an exception is raised, then the first matching `except` clause handles it. Catch the most specific exception class possible (`except FileNotFoundError:`, `except KeyError:`) rather than bare `except:` or `except Exception:`, which hide bugs like typos (NameError) and swallow KeyboardInterrupt in the bare form. Multiple types are caught with a tuple: `except (ValueError, TypeError) as exc:`.

The full statement is try/except/else/finally: `else` runs only when the try block raised nothing, which keeps the happy path out of the exception scope, and `finally` always runs, even on return or unhandled exceptions, making it the place for cleanup. For resources like files, locks, and connections, the `with` statement (context manager) is preferred over manual finally blocks: `with open(path) as f:` guarantees the file closes on any exit path.

Exception chaining: inside an except block, `raise NewError("context") from exc` records the original exception as `__cause__`, producing a traceback with "The above exception was the direct cause". A bare `raise` re-raises the current exception unchanged, preserving its traceback — use it when you want to log and propagate. `raise ... from None` suppresses the chained context when the original exception is an implementation detail.

Define custom exceptions by subclassing Exception, usually as a small hierarchy rooted in one base class per library (`class AppError(Exception)`, then `class ConfigError(AppError)`), so callers can catch either the specific or the general class. Attach structured data as attributes in `__init__` instead of encoding everything into the message string. Never subclass BaseException; that level is reserved for exits like SystemExit and KeyboardInterrupt.

EAFP ("easier to ask forgiveness than permission") is idiomatic Python: attempt the operation and catch the failure (`try: value = d[key] except KeyError:`) rather than pre-checking (LBYL, "look before you leap"). EAFP avoids time-of-check/time-of-use races and double lookups. Pre-checking remains fine when a check is clearer and cheap, such as `if path.exists()` for user-facing messages — but the authoritative handling should still catch OSError, since the file can vanish between check and use.

Python 3.11 added exception groups and `except*` for handling multiple simultaneous failures, raised naturally by `asyncio.TaskGroup` when several concurrent tasks fail. `except* ValueError as eg:` matches ValueError members inside an ExceptionGroup, and multiple `except*` clauses can each fire for their own subset. 3.11 also added `Exception.add_note()` to attach extra context strings that appear in the traceback.
