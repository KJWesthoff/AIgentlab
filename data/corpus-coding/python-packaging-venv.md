# Python packaging, virtual environments, and dependencies

A Python virtual environment isolates a project's installed packages from the system interpreter and from other projects. Create one with `python -m venv .venv`, activate it with `source .venv/bin/activate` (Linux/macOS) or `.venv\Scripts\activate` (Windows), and deactivate with `deactivate`. Activation just edits PATH; running `.venv/bin/python` or `.venv/bin/pip` directly works without activation. Each project should have its own venv, and `.venv/` belongs in `.gitignore`.

Modern Python packaging is configured in `pyproject.toml`, which replaces `setup.py` and `setup.cfg` for new projects. The `[project]` table declares name, version, `dependencies` (a list of requirement strings), and `[project.optional-dependencies]` for extras such as a `dev` group installed via `pip install -e ".[dev]"`. `[project.scripts]` maps command names to entry-point functions (`mycli = "mypkg.main:main"`), which is how a package installs a CLI command onto PATH.

An editable install, `pip install -e .`, links the package to the source tree so code edits take effect without reinstalling — the standard setup for development. The src layout (`src/mypkg/...` instead of `mypkg/` at the repo root) is recommended because it prevents accidentally importing the uninstalled working-copy package from the current directory, forcing tests to run against the installed package.

Version pinning: applications should pin exact dependency versions in a lock file for reproducible deployments, while libraries should declare loose ranges (`httpx>=0.27`) to stay compatible with consumers. `pip freeze > requirements.txt` snapshots the current venv. The `uv` tool is a fast drop-in replacement for pip and venv workflows (`uv venv`, `uv pip install`, `uv lock`), and Poetry and PDM manage pyproject-based projects with their own lock files.

Common environment errors: "ModuleNotFoundError: No module named X" usually means the package was installed into a different interpreter than the one running — check `which python` and `python -m pip list`, and prefer `python -m pip install` over bare `pip` so the interpreter and installer always match. "externally-managed-environment" errors on Linux mean the system Python refuses global pip installs; the fix is to use a venv (or pipx for standalone CLI tools).

Relative versus absolute imports: within a package, `from .sibling import thing` imports relative to the current package and only works when the code is run as part of the package (`python -m mypkg.main`), not as a loose script (`python main.py`), which raises "attempted relative import with no known parent package". Installing the project editable and using absolute imports (`from mypkg.sibling import thing`) avoids the whole class of path-hacking with sys.path.
