# TypeScript configuration (tsconfig) and the module system

`tsconfig.json` configures the TypeScript compiler. The most important setting is `"strict": true`, an umbrella that enables strictNullChecks (null/undefined are distinct types), noImplicitAny (untyped parameters are errors instead of silently `any`), strictFunctionTypes, strictPropertyInitialization, and useUnknownInCatchVariables. New projects should always start strict; retrofitting strictness later is far more work than starting with it.

Key compilerOptions: `target` sets the emitted JavaScript version (`ES2022` is a safe modern choice), `module` and `moduleResolution` control the module format and how imports are resolved (`"module": "NodeNext"` for Node.js projects, `"module": "ESNext"` with `"moduleResolution": "Bundler"` when a bundler like Vite or esbuild does the resolving), `outDir` places emitted files, `rootDir` sets the source root, `declaration` emits `.d.ts` type declaration files for libraries, and `sourceMap` enables debugger stepping through original sources.

ES modules versus CommonJS is the main source of Node/TypeScript import errors. CommonJS uses `require()`/`module.exports`; ES modules use `import`/`export` and are enabled in Node by `"type": "module"` in package.json or the `.mjs` extension. With `"module": "NodeNext"`, TypeScript enforces Node's real rules: relative imports in ES modules must include the `.js` extension in the import specifier (`import { x } from "./util.js"`), which refers to the emitted file even though the source is `util.ts`. "ERR_REQUIRE_ESM" means CommonJS code tried to require an ESM-only package; the fixes are dynamic `import()`, migrating the project to ESM, or using a version of the dependency that ships CommonJS.

`esModuleInterop: true` fixes default-import mismatches between CommonJS modules and ES import syntax, allowing `import express from "express"` instead of `import * as express`. `skipLibCheck: true` skips type-checking dependency declaration files, a widely used pragmatic speedup. `paths` in tsconfig defines import aliases such as `"@/*": ["./src/*"]`, but it only affects type checking — the runtime or bundler must also be configured to resolve the same aliases.

Type declarations for JavaScript dependencies come from bundled `.d.ts` files or from the DefinitelyTyped packages `@types/*` (e.g. `npm i -D @types/node` provides Node builtin types, required for `process`, `fs`, and `__dirname` to type-check). The error "Cannot find module 'x' or its corresponding type declarations" (TS2307) usually means either the package is not installed, types are missing (install `@types/x`), or moduleResolution does not match how the package exposes its entry points via package.json `exports`.

Running TypeScript: `tsc` type-checks and emits JavaScript; `tsc --noEmit` type-checks only, the standard CI step when a bundler handles emitting. `tsx` runs TypeScript directly with near-zero setup and is the common dev-time runner (`tsx watch src/main.ts`); Node 22+ can also run TypeScript files natively by stripping types. Bundlers and runners generally do not type-check at all, so a separate `tsc --noEmit` remains necessary to actually catch type errors.
