# TypeScript types: interfaces, unions, and narrowing

TypeScript adds static types on top of JavaScript; types are erased at compile time and never exist at runtime. `interface` and `type` aliases both describe object shapes and are interchangeable for most uses. Differences: an interface can be extended via declaration merging (two declarations with the same name merge), while a type alias can express unions, tuples, mapped types, and conditional types that interfaces cannot. Common guidance: use interface for public object shapes and type for unions and compositions.

A union type `string | number` means a value is one of several types, and TypeScript only allows operations valid on every member until the union is narrowed. Narrowing happens through control flow analysis: `typeof x === "string"` for primitives, `x instanceof Date` for classes, `"key" in obj` for property presence, equality checks against literal values, and truthiness checks. After a narrowing check, the variable's type inside that branch is reduced automatically — no casts needed.

Discriminated unions (tagged unions) are the idiomatic way to model variants: give each member a common literal property, such as `{ kind: "circle"; radius: number } | { kind: "square"; size: number }`, then `switch (shape.kind)` narrows each case to the exact member. Add an exhaustiveness check in the default branch by assigning to `never` (`const _exhaustive: never = shape`), so adding a new variant produces a compile error at every unhandled switch.

`unknown` versus `any`: `any` disables type checking entirely in both directions and spreads through code, while `unknown` is the type-safe top type — you can assign anything to it, but you must narrow it before use. Prefer `unknown` for values from JSON.parse, catch clauses, and external input. `never` is the empty type for impossible states and functions that never return; `void` means a function returns nothing useful.

Optional and nullable handling: a property declared `name?: string` has type `string | undefined`. With `strictNullChecks` enabled, `null` and `undefined` are not assignable to other types, forcing explicit handling. Optional chaining `user?.address?.city` short-circuits to undefined, and the nullish coalescing operator `value ?? fallback` substitutes only for null/undefined (unlike `||`, which also replaces empty string and 0). The non-null assertion `x!` tells the compiler to trust you and should be rare.

Type assertions with `as` override the compiler's inference (`data as User`) but perform no runtime conversion or validation — asserting a wrong type produces runtime errors later. For external data (API responses, file contents), assertions are unsafe; validate at the boundary with a schema library such as Zod (`UserSchema.parse(data)` returns a typed, validated value) or write a user-defined type guard: `function isUser(x: unknown): x is User` returning a boolean, which the compiler uses for narrowing.
